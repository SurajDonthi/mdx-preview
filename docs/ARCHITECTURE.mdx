# Architecture

How the code works, for anyone changing it.

This repository is a library first and an application second. The parser, the
renderer, the components and the exporter live in `packages/*` and know nothing
about the Studio. `apps/studio` is one consumer of them — the one that proves
the packages compose, and the one you are probably reading this in.

<Callout type="info" title="Two things to understand first">
  The **registry** decides what a document may name, and the **render mode**
  decides where the document's code runs. Everything else follows from those two.
</Callout>

---

## The workspace

npm workspaces, declared in the root `package.json` as `packages/*` and `apps/*`.
Each package is independently consumable and carries only the dependencies it
actually needs, which is the whole reason for the split: a host that wants
callouts and code blocks should not download Mermaid, Recharts and jsPDF to get
them.

| Package | What it is | Costs you |
| --- | --- | --- |
| `@mdxkit/core` | Types, the MDX parser, the expression evaluators, the plugin registry, the render context | `unified`, `remark-*`, `js-yaml`, two `estree-util-*` helpers |
| `@mdxkit/react` | `MdxRenderer`, the built-in components, the theme presets, the base stylesheet | `hast-util-to-jsx-runtime`, `prismjs`, `lucide-react` |
| `@mdxkit/mermaid` | `MermaidDiagram`, and the plugin that claims the mermaid code fence | `mermaid` |
| `@mdxkit/charts` | `Chart`, backed by Recharts and loaded on demand | `recharts` |
| `@mdxkit/flow` | `FlowGraph`, the interactive node/edge diagram | `lucide-react` |
| `@mdxkit/pdf` | The A4 exporter | `jspdf`, `html2canvas` on the fallback path only |
| `@mdxkit/sandbox` | Renders a document you do not trust, in an isolated frame | nothing beyond core and react |

`@mdxkit/react` deliberately does **not** depend on Mermaid, Recharts or the
flow renderer. It cannot: they are what a host opts into.

## The registry

`packages/core/src/registry.ts`.

A document is rendered against one flat `name -> component` map. The renderer
resolves every JSX tag through it and hands the same map to expressions as their
scope, so **a document can only reach what the host put in the registry**. A tag
that is not in it renders a small notice naming it, and the surrounding document
carries on.

Packages do not export that map directly. They export *plugins*, and the
application composes them:

```ts
// apps/studio/src/mdxRegistry.ts
import { createRendererRegistry } from '@mdxkit/react';
import { mermaidPlugin } from '@mdxkit/mermaid';
import { chartsPlugin } from '@mdxkit/charts';
import { flowPlugin } from '@mdxkit/flow';

export const studioMdxRegistry = createRendererRegistry(
  mermaidPlugin,
  chartsPlugin,
  flowPlugin
);
```

`createRendererRegistry()` is `createMdxRegistry()` with `reactPlugin` already
first, so the built-ins are always present.

A plugin is plain data with three optional parts:

```ts
export const mermaidPlugin = defineMdxPlugin({
  name: '@mdxkit/mermaid',
  components: { MermaidDiagram },
  aliases: { Mermaid: 'MermaidDiagram' },
  codeFences: { mermaid: 'MermaidDiagram' },
});
```

- **`components`** are tag names a document may write.
- **`aliases`** are extra names for a component *anything* registered, not only
  something this plugin registered.
- **`codeFences`** claim a fenced language. When a document contains a mermaid
  fence, `CodeBlock` in `packages/react/src/MdxRenderer.tsx` looks the language
  up in `registry.codeFences` and mounts the named component as
  `<MermaidDiagram language="mermaid">` with the fence body as its children,
  instead of syntax-highlighting the block. Languages are matched lower-cased.

Three rules in `createMdxRegistry` are worth knowing before you change it, each
of them load-bearing and each covered by `packages/core/tests/registry.test.ts`:

- **Sources apply in order and the last one wins.** That is how an application
  replaces a component a package shipped — list your own version last. A bare
  component map is accepted alongside plugins for exactly this.
- **Aliases and fences resolve after every source has contributed**, not as each
  source is applied. A plugin may therefore alias a component another plugin
  provides, in either listing order.
- **An alias or fence pointing at nothing throws, naming the plugin.** A silent
  `undefined` in the map would surface much later as an unrenderable tag.

`defineMdxPlugin` only adds a symbol brand. Without it the object is merged as
a component map, and `name` and `components` become tag names — which is exactly
the failure the brand exists to prevent.

## The render pipeline

`packages/react/src/MdxRenderer.tsx`, with the parsing half in
`packages/core/src/mdxAst.ts`.

<Callout type="note" title="No JavaScript is generated for the document">
  Earlier versions cut the document into markdown and JSX chunks with a
  hand-written scanner and compiled the JSX chunks with Babel at runtime. That is
  gone. The document is parsed into a tree and the tree is turned into React
  elements. Only the expressions written inside it are ever evaluated, and only
  as far as the `expressions` prop allows.
</Callout>

In order:

1. **Frontmatter split.** `parseFrontmatter()` peels the YAML header with
   `js-yaml`. `countLines()` measures what was removed so every position the
   parser later reports is shifted back onto the file the author is editing.
2. **Parse.** `parseMdxDocument()` runs the body through
   `remark-parse` → `remark-gfm` → `remark-mdx` → `remark-rehype`, with the five
   MDX node types listed in `passThrough` so `remark-rehype` does not drop them.
   The result is a hast tree with the MDX nodes still in it. It never throws: a
   syntax error comes back as a located `MdxParseError`.
3. **Sanitise and register slots.** The same pass drops what the renderer cannot
   use — `import`/`export`, empty or comment-only expressions, attributes whose
   expression carries no ESTree — reporting each as a diagnostic. Every surviving
   expression is recorded in `ast.slots`, keyed by the identity of its ESTree
   node.
4. **Normalise.** `unwrapBlockJsx()` lifts a block-level tag out of the paragraph
   MDX left it in; `assignHeadingIds()` stamps ids from `collectHeadings()`.
5. **Render.** `toJsxRuntime()` from `hast-util-to-jsx-runtime` walks the tree
   with the registry as its component map and a custom `createEvaluater`.
6. **Contain failures.** `MdxErrorBoundary` catches anything a component throws;
   `resetKey` clears it as soon as the document changes, so fixing the typo also
   clears the banner.

### Why the slot map exists

`hast-util-to-jsx-runtime` calls `evaluateExpression` for two different things:
the expressions the author wrote, and the synthetic identifier lookups it
performs to resolve a capitalised tag name. They arrive at the same function and
look alike.

`ast.slots` is what tells them apart. An expression node present in the map is
the author's and goes to the evaluator; one that is absent is a tag name and goes
to `resolveComponent()`, which walks dotted paths against the scope and falls
back to the unknown-component notice. Get this wrong and either every
`<Callout>` becomes a scope lookup failure, or every author expression silently
resolves to a component.

### Parsing is cached, deliberately shared

`parseMdxDocument()` keeps the last four results keyed by body and offset. The
application asks for the same document twice on every keystroke — once for the
table of contents, once to render it — and the export pass can ask a third time.
Handing every caller the same object keeps that to one parse.

The consequence is that the tree is **shared and mutable**. Stamping heading ids
and unwrapping block JSX are safe only because doing them twice changes nothing.
Anything you add there must have the same property.

### Expressions

`packages/core/src/estreeEval.ts`. `MdxRenderer` picks an evaluator from its
`expressions` prop:

- **`'full'`** (the default) serialises the expression's ESTree back to
  JavaScript — lowering any JSX inside it to `createElement` calls first — and
  runs it through `new Function` with the registry bound as parameters. Real
  JavaScript semantics, for one expression at a time. A document can map over
  data and build elements inline. Compiled functions are cached by source text.
- **`'literals'`** walks the tree by hand and builds only what the syntax spells
  out: strings, numbers, booleans, `null`, arrays, plain objects, and template
  literals with no substitutions. Identifiers, member access, calls, arrow
  functions, JSX and spreads are all refused with a reason. Nothing executes.

`'literals'` is for a host that renders content it did not write and is *not*
sandboxing. It is a real reduction in reach, not a security boundary: a document
still chooses which registered components to mount and what to pass them.

Failures never propagate. An expression that will not evaluate produces a console
warning naming the attribute and its line, and the value is omitted — the
document renders without it.

### What a broken document looks like

Three distinct failure modes, none of which blanks the preview:

| Failure | What the reader sees |
| --- | --- |
| The body does not parse | A banner reading `MDX: Line 6, Column 17 - ...`, over the last tree that did parse |
| A tag is not in the registry | An inline notice naming the tag; its children still render |
| A component throws | The boundary's card with the thrown message; the rest of the page stays |

The last-good-render behaviour matters more than it looks: a document is
mid-syntax on most keystrokes, so without it the preview would strobe.

## In-page or sandboxed

There are two ways to put a document on screen, and the difference is where the
document's code runs.

**`MdxRenderer` runs it in the page**, with the page's origin. For a document the
user wrote, that is correct and cheap. For one an LLM generated or a stranger
pasted, it is fatal: expressions in `'full'` mode are real JavaScript with access
to `localStorage`, cookies, the session token and the app's own API.

**`SandboxedMdx` runs it in an iframe with an opaque origin.** The approach is
isolation, not restriction: the document keeps every capability it had — state,
handlers, inputs, arbitrary components — but it has nowhere to spend them.

Four pieces make the boundary, and each of them has a reason spelled out in the
source:

- **`sandbox="allow-scripts"` and nothing else** — `packages/sandbox/src/host/frameDocument.ts`.
  Omitting `allow-same-origin` is what produces the opaque origin. The two
  together would hand the frame the app's origin *and* the ability to strip its
  own sandbox attribute.
- **A CSP delivered as a `meta` element**, because a `srcdoc` document has no
  HTTP response to carry a header. `connect-src 'none'` is the important one:
  it removes fetch, XHR, WebSocket, EventSource and `sendBeacon`. `img-src` is
  `data: blob:` and not `https:` on purpose — a remote image URL is a GET with a
  payload, and it works even when `connect-src` is closed. `script-src` does
  allow `unsafe-eval`, because evaluating an expression means `new Function`;
  that is affordable precisely because the frame has no origin, no storage and
  nowhere to send anything.
- **A sealed envelope**, `packages/sandbox/src/protocol.ts`. Every page shares one
  `message` stream, and a sandboxed frame's origin serialises as the *string*
  `"null"` for every such frame on the page — so origin cannot identify ours. The
  host pins `event.source` identity first and a per-instance channel secret
  second.
- **The capability table**, `packages/sandbox/src/host/types.ts`. It is looked up
  with `hasOwnProperty`, so a document cannot call `constructor` or `toString`
  and reach the prototype chain. Calls time out, and there is a ceiling on how
  many may be outstanding.

The guest has to be handed its runtime as source text — it has no origin to fetch
from — so `packages/sandbox/src/build/` bundles a guest entry into one IIFE with
esbuild and exposes it as an importable string through a Vite plugin. That bundle
is a second, independent module graph; nothing from the application's scope can
reach the frame by accident.

<Callout type="warning" title="Sandbox is not wired into the Studio">
  `@mdxkit/sandbox` is complete and tested but no application in this repository
  mounts it — the Studio only ever renders documents its own user wrote. Adding a
  paste-a-document or share-a-link feature is the point at which it stops being
  optional.
</Callout>

## Adding a component

1. Write it in the package it belongs to. Something that only costs React goes in
   `packages/react/src/CustomComponents.tsx`; anything that drags a library with
   it gets its own package.
2. Register it: add it to `baseMdxComponents` at the bottom of that file, or to
   your package's `defineMdxPlugin` call.
3. If it renders differently in the export pass, read `MdxRenderContext` from
   `@mdxkit/core`. It gives you `renderMode` and `themeCategory`, so nothing has
   to be threaded through the tree as props.
4. Style it with `--mdxkit-*` custom properties in your package's `styles.css`.
   No Tailwind, no build step — see the styling section of the README.

Constraints worth designing around:

- **Handle malformed props.** Document authors hand-write JSON. Every built-in
  clamps its own inputs: `ProgressBar` checks its colour against a set,
  `CardGrid` snaps `cols` to two, three or four, `Accordion` defaults `items` to
  an empty array.
- **The PDF exporter deletes every `button` element** and everything marked
  `data-pdf-interactive`. Do not put content inside one that the reader needs.
- **Mobile matters.** Anything that can be wider than the pane has to scroll
  inside itself: `min-width: 0` and `overflow-x: auto` on the wrapper, never on
  the page.

## State and persistence

This part belongs to `apps/studio` alone; the packages hold no state.

`App.tsx` owns `documents[]`, `activeDocId`, `mdxContent`, `documentTitle`,
`currentDriveFileId` and `currentUser`. One debounced effect (400ms) is the only
write path, and it fans out to localStorage, then Firestore, then Drive.

**Timestamps decide sync conflicts**, so `saveDocument()` in
`apps/studio/src/utils/storage.ts` only advances `updatedAt` when the title or
content genuinely changed. Opening a document or signing in must not bump it —
otherwise a merely-opened stale copy beats a real edit made on another device.

**Deletion writes tombstones**, locally and in Firestore, rather than removing
rows. Without them another device still holding the document re-uploads it on its
next save and the subscription hands it straight back. Tombstones self-prune
after 30 days.

**Firestore documents live under each user's own `documents` subcollection.**
They used to sit in a flat global collection keyed by document id, which meant
the fixed sample ids collided across accounts and two users shared one record.
Seeded sample ids now carry a per-install suffix as well.
`migrateLegacyDocuments()` copies forward from the old path once per account per
browser and does not delete the originals.

**A newer copy arriving while you type does not overwrite the buffer.** The sync
effect compares three signatures — what is in the editor, what was last
persisted, and what just arrived — and only adopts the incoming version when
there is no unsaved work to lose. When there is, it keeps the local text and says
so once per incoming version rather than once per snapshot.

<Callout type="error" title="Rules do not cascade into subcollections">
  A Firestore rule matching only the user record leaves every document read and
  write denied. The rule matching the documents subcollection is what actually
  protects them, and it must be deployed with the code. See CONFIGURATION.mdx.
</Callout>

**Google Drive is opt-in and manual.** A document only syncs to Drive once you
have saved it there from the Drive modal, which sets `driveFileId`. After that
the auto-save effect patches its content. The `drive.file` scope means the app
only ever sees files it created.

## PDF export

`packages/pdf/src/pdfExporter.ts`.

When the export dialog opens, `App.tsx` mounts a second copy of `MdxRenderer`
off-screen with `renderMode="pdf"` inside `.pdf-export-root`. Export then:

1. waits for every Mermaid diagram to reach `ready`, failing loudly if any errored
2. clones the tree, rasterises each diagram's SVG to PNG, and applies light-mode
   styles with `!important`
3. captures it by serialising the clone into an SVG `foreignObject` and drawing
   that into a canvas — **the browser's own layout engine draws the page**
4. slices the canvas into A4 pages at boundaries measured to avoid splitting
   protected blocks
5. writes the pages into a `jsPDF` document and downloads it

### Why foreignObject and not html2canvas

html2canvas reimplements CSS layout in JavaScript. It draws a bordered inline box
where CSS says, but paints that box's *text* about 10px lower — measured constant
across flex, inline-block, block, float and table-cell, across five font stacks,
five font sizes, padding sweeps and relative positioning. Every pill label sat
below its own border and every icon floated above its label, and no styling could
correct it.

Rendering through `foreignObject` hands layout back to the browser, so the
capture matches the screen. Verified on Chromium, WebKit and Gecko.

Three portability details that path requires, each of which was a real failure:

- **Ship the stylesheets, do not copy computed styles.** Every engine enumerates
  a different property set from `getComputedStyle`, and whatever it omits
  vanishes from the capture — WebKit lost CSS grid columns that way.
- **Pin image sizes.** An `img` sized `auto` has nothing to resolve against
  inside a detached SVG; WebKit collapsed every diagram to zero height.
- **Use a `data:` URL, not a blob.** Chrome treats a blob-URL SVG as cross-origin
  and taints the canvas, which blocks `toDataURL`.

If the capture fails or comes back blank, `html2canvas` loads dynamically as a
fallback so the export never hard-fails. It is not in the main bundle.

`exportHtmlToPdfVector` and `exportHtmlToPdf` are aliases of
`exportHtmlToPdfCanvas`, kept so older callers still resolve. There is no vector
path; the name is a leftover.

## Tests

`vitest.config.ts` defines four projects, each rooted at the workspace it tests:
`core` in node, and `react`, `sandbox` and `studio` in jsdom — the renderer
mounts real trees, the sandbox bridges drive the real host and guest code against
fake windows, and `storage.ts` talks to localStorage. `npm run test:run` runs all
four; CI runs lint, build and tests on both Ubuntu and Windows.

The Windows leg is deliberate. A lockfile only carries Windows native binaries
for rollup, esbuild and `@tailwindcss/oxide` if it was generated with every
platform's optional dependencies resolved, and a Linux-only matrix is exactly
what hid that being missing.

## Known architectural debt

- **Conflict resolution is last-writer-wins** on client clocks. There is no merge
  UI.
- **`'full'` expression mode is not a security boundary** and is the default. A
  host rendering content it did not write has to opt into `'literals'` or into
  the sandbox; nothing forces the choice on it.
- **The parse cache assumes idempotent mutation** of a shared tree. It is
  correct today and there is no assertion protecting it.
- **The whole guest runtime is inlined into an HTML attribute.** It has to be —
  the frame has no origin to fetch from — but the frame document is rebuilt from
  scratch whenever the runtime, the styles or the CSP change, and rebuilding it
  remounts the document.
- **The Studio bundle is a single ~4 MB chunk.** Mermaid's diagram types and
  Recharts already code-split themselves; the renderer, Prism, Firebase and the
  app do not. `npm run build` prints the current figures.
