# Document Lifecycle — Full Trace

Every place a document is created, changed, saved, synced or deleted, traced from the
source. Read the **map** first, then step through the **flows**, then the
**discrepancies** — that last section is the point of this document.

Each flow below shows the *same* architecture, with only that flow's path coloured.
Switch tabs to switch the highlighted path.

<Callout type="warning" title="Read this first">
  Eight of the discrepancies below are behavioural, and two of those can lose or cross
  contaminate document content. They are ranked by blast radius at the end, with exact
  file and line references.
</Callout>

---

## The Map

Four layers. The React tree holds all state; three persistence modules sit behind it;
each talks to one external system. Nothing talks to an external system directly from a
component except the Drive modal.

keyboard-focus any node for what it actually does. Solid arrows are writes; dashed

## Discrepancies

Ranked by blast radius. Every one was read out of the source, not inferred.

<Callout type="success" title="All nine have since been fixed">
  This section is kept as the as-found audit record, so the reasoning behind each fix
  stays readable. The file and line references below point at the code as it was when
  the audit ran, not as it is now. See ARCHITECTURE.md for the current design, and the
  git history for what each fix changed.
</Callout>

| # | Severity | What happens | Where |
|---|---|---|---|
| D1 | **Critical** | Two different users share one Firestore document | `firestoreService.ts:20` |
| D2 | **High** | Opening a document makes it "newer" than the cloud copy | `App.tsx:154`, `storage.ts:106` |
| D3 | **High** | Renaming never renames the Drive file | `driveService.ts:151` |
| D4 | **Medium** | Drive sync failures are silent, UI still says saved | `App.tsx:143` |
| D5 | **Medium** | "Drive connected" shows without a Drive token | `App.tsx:88` |
| D6 | **Medium** | Sample documents get uploaded to every new account | `App.tsx:112` |
| D7 | **Medium** | Deleted documents can come back | `App.tsx:212` |
| D8 | **Low** | Drive browser lists more than MDX files | `driveService.ts:87` |
| D9 | **Low** | Dead code and unused fields | three places |

### D1 · Firestore document ids collide across users

`saveDocumentToFirestore` writes to `doc(db, 'documents', document.id)` — a **global**
collection keyed by the document's own id. The four seeded samples use fixed ids
(`mermaid-pdf-test`, `all-in-one-showcase`, `developer-docs`, `blog-post`), and every
new install seeds those same ids.

So the moment two users sign in, they are both writing to the Firestore document
literally named `mermaid-pdf-test`. The listener filters by `userId`, so whoever wrote
last owns the record and the other user's copy silently becomes the other person's
content — or vanishes from their list when `userId` no longer matches.

<Callout type="warning" title="This is a cross-account data leak, not just a bug">
  User B can read User A's edits to any sample-derived document, because they are the
  same Firestore record. Giving each account its own documents subcollection under its
  own uid record fixes it, as does seeding installs with unique ids.
</Callout>

### D2 · Merely opening a document rewrites its timestamp

Two things combine:

- `saveDocument()` always overwrites `updatedAt` with `new Date()`, whether or not the
  content changed — `storage.ts:106`.
- The auto-save effect lists `activeDocId` and `currentUser` in its dependencies, so it
  fires on **document switch** and on **login**, not just on edits — `App.tsx:165`.

`mergeDocuments` then compares those timestamps to decide a winner. Because opening a
document freshens its local timestamp, the local copy nearly always wins.

**Concrete loss:** edit a document on your phone, then merely *open* it on your laptop
without typing. The laptop's stale copy is now newer, and the next save overwrites your
phone's edits.

There is a second, quieter effect of the same cause: the sidebar sorts by `updatedAt`,
so just clicking through documents reshuffles the list.

<Callout type="info" title="Why it isn't worse than it is">
  Switching documents also re-runs the effect and its cleanup clears the pending timer,
  so the *previous* document's content is not written under the *new* document's id.
  That safety depends entirely on a re-render landing inside 400ms — it works, but it is
  holding a sharp edge.
</Callout>

### D3 · The Drive update path never sends a filename

`saveFileToDrive` has two branches. Creating a file does a multipart upload with
`metadata.name`. Updating does `PATCH ...?uploadType=media` with **only the body** — no
metadata part, so the name is never touched.

It then returns `{ name: cleanName }` anyway, so the caller is told a rename happened.
Renaming a Drive-linked document therefore changes the title everywhere except Drive,
permanently, and the app reports success.

### D4 · Drive sync fails silently during auto-save

In `executeSave`, the Drive call is wrapped in `try/catch` that does
`console.warn` and continues. `setIsSaving(false)` runs regardless, so the UI reports a
clean save. An expired token — which the Drive modal handles carefully with a
`TOKEN_EXPIRED` path — is simply swallowed here. You can edit for an hour believing
Drive is current when nothing has reached it since the token expired.

### D5 · "Drive connected" is derived from the wrong signal

`App.tsx` calls `initAuth((user) => { setCurrentUser(user); setIsDriveConnected(true); })`.
The callback's second parameter is the Drive access token, and it is ignored. So
`isDriveConnected` is true whenever Firebase auth is restored, even when
`localStorage.google_access_token` is absent or expired.

The sidebar then shows Drive as active, and the auto-save Drive branch is gated on a
token that may not exist — so the badge and the behaviour disagree.

### D6 · First login uploads the sample documents

`if (cloudDocs.length === 0 && localDocs.length > 0) localDocs.forEach(saveDocumentToFirestore)`.

On a first sign-in the local set is the four seeded samples, so every new account gets
them pushed to the cloud. Worse, the condition is on *any* empty snapshot, so a
transient empty read re-uploads whatever is local at that moment.

### D7 · Deletion has no tombstone

Delete removes the document from localStorage and from Firestore, and errors from the
Firestore call are swallowed. Nothing marks the id as deleted. Any other device still
holding it locally will re-upload it on its next auto-save, and your listener puts it
straight back in your list. The Drive file is never removed under any path.

### D8 · The Drive browser lists everything it can see

`listDriveFiles` runs two queries and merges. The second is
`trashed=false and mimeType != 'application/vnd.google-apps.folder'` with no extension
or MIME filter and `pageSize=50`. The panel is headed "Your Google Drive MDX Files" but
shows any file the app's `drive.file` scope can reach, newest 50.

### D9 · Dead code and unused fields

- `DocumentManagerModal.tsx` — 10KB component, imported by nothing.
- `StoredDocument.lastSyncedToDriveAt` — declared at `storage.ts:9`, never written or read. The very field that would fix D2's comparison problem exists but is unused.
- `auth.ts` — `isSigningIn` is assigned in two places and never read.

## How the map is drawn

The map at the top is a `FlowGraph` — an inline-SVG component registered in
`CustomComponents.tsx` and driven entirely by the JSON graph in this document. Nodes,
edges, layer bands and the eight flows are all data; the component owns every piece of
interaction, because the MDX scope here compiles JSX expressions only and a document
cannot declare state of its own.

- **Flows panel** sits to the right on a wide preview and stacks underneath below about
  760px, so the diagram never forces the page sideways.
- **Selecting a flow** dims everything off the path and numbers the nodes in order.
- **Hover, tap or keyboard-focus a node** for its description; tab reaches every node.
- **PDF export** drops the interaction and prints the full graph plus a static list of
  all eight flows with their complete paths written out.

The per-flow tabs above keep their Mermaid diagrams — they show the internal branching
of each flow, which the map deliberately does not.
